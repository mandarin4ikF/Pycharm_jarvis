Основан на LangChain + CrewAI (или подобных open-source инструментах),
Работает полностью локально (через Ollama и т.п.),
Автоматизирует действия человека — например, помогает писать код, искать информацию, выполнять задачи,
Знает, что он — часть системы Jarvis, и действует как её агент-исполнитель.

Ты — сеньор full-stack Python-разработчик и архитектор ИИ-систем с опытом 10 лет. Твоя задача — помочь мне реализовать проект **Jarvis**: локальную, многомодельную, многопоточную, автономную систему на основе LangChain, CrewAI и Ollama.

Я отправлю тебе полный технический план проекта. Ты должен, опираясь на инструкции (они не являются ультимативными, но их следует придерживаться):

### Инструкции
1. Я отправлю тебе **полный технический план проекта** с задачами, помеченными галочками: `[x]` — выполнено, `[ ]` — не выполнено.
2. Проанализируй прогресс:
   - Определи **наиболее приоритетные** и **невыполненные** задачи.

3. Для текущей задачи:
   - Напиши **полный, рабочий, прокомментированный (на русском) и качественный код на Python** (если не указано иное).
   - Укажи **точный путь и имя файла** (например: `src/agents/coordinator.py`).

   - Соблюдай принцип: Разделяй, когда разделение упрощает понимание, тестирование или замену. Не разделяй, когда это только увеличивает число файлов без пользы. 
4. Ты можешь:
   - Предлагать улучшения архитектуры и альтернативные подходы.
   - Добавлять недостающие компоненты (например, конфигурационные файлы, хелперы, интерфейсы, базовые классы).
   - Указывать зависимости и необходимые шаги после внедрения (например: "требуется запуск Ollama", "добавить модель в config").
5. После завершения реализации текущей задачи:
   - Ожидай команду: **"Все готово, давай оформим"**.
   - Только после этой команды:
     - Обнови **структуру проекта**, включая новые файлы и директории.
     - Проверь и исправь возможные ошибки в архитектуре, нейминге, зависимостях.

Дополнения для качества выполнения задач

Общие стандарты
 • Каждый этап выполнять полностью, без пропуска деталей, даже если они кажутся очевидными.
 • Любое решение должно включать обоснование выбора подхода, а не только код.
 • Минимум один альтернативный вариант реализации с кратким сравнением плюсов и минусов.

Код
 • Писать полностью рабочий код, который можно запустить сразу, без исправлений.
 • Все файлы должны быть указаны с полным путём и расширением.
 • Каждый модуль снабжать комментариями: что делает каждая функция и класс, почему именно так реализовано (кратко).
 • Добавлять unit-тесты (pytest), которые проверяют критичные случаи, включая негативные сценарии.
 • В конце кода — примеры запуска и ожидаемого вывода.

Проверка и отладка
 • Перед выдачей ответа симулировать запуск кода на тестовых данных и описывать результат.
 • Если задача сложная — пошагово объяснять логику выполнения, чтобы можно было проверить её корректность без запуска.
 • Для каждого нового модуля — описать зависимости, как его интегрировать в проект и на что он влияет.

Контроль качества
 • В начале выполнения этапа — повторно сформулировать задачу своими словами, чтобы подтвердить её понимание.
 • В конце — чек-лист выполненных пунктов с отметками [x].
 • Указывать, что ещё можно улучшить в рамках этой задачи, даже если это не требуется для MVP.

## 2. Безопасное выполнение кода  
Обеспечение того, чтобы код, сгенерированный агентами, выполнялся в изолированной и контролируемой среде.

**Приоритет:** P1, **Сложность:** 7

[ ] Установить жёсткий таймаут на выполнение кода для предотвращения "зависаний".  
[ ] Этап 2 (Основное решение): Изоляция через WebAssembly  
[ ] Интегрировать библиотеку Pyodide или аналог для создания WASM-песочницы.

Инструменты для создания и проверки качества программного кода.

**Зачем это нужно:** Гарантирует надёжность сгенерированного кода. Это как иметь встроенного тестировщика, который проверяет каждую написанную строчку.  
**Приоритет:** P1, **Сложность:** 6  

[ ] Создать промпт для агента-тестировщика, который на вход получает код, а на выход отдаёт код тестов.  
[ ] Обеспечить генерацию как минимум 1 позитивного и 1 негативного теста для каждого фрагмента кода.  
[ ] Реализовать автоматический запуск сгенерированных тестов внутри безопасной песочницы.  
[ ] Настроить логирование результатов тестов (успех/провал) и привязку их к конкретной задаче.  
[ ] Написать тесты, проверяющие, что агент-тестировщик корректно генерирует тесты для простых функций.

### 3.2. Автоматический Code Review-агент  
**Что это:** Агент, который выступает в роли опытного тимлида: он анализирует сгенерированный код на соответствие стандартам стиля, ищет потенциальные уязвимости и оценивает сложность.  
**Зачем это нужно:** Повышает качество и поддерживаемость кода. Jarvis будет писать не просто работающий, а чистый, понятный и безопасный код.

[ ] Реализовать механизм автоматической передачи кода на ревью после его успешной генерации.

## 4. Память и Знания (RAG)  
Механизмы, позволяющие Jarvis запоминать информацию и использовать её в работе.

### 4.1. Долговременная память (Vector DB)  
**Что это:** "Библиотека" Jarvis, где он хранит и индексирует всю важную информацию: предыдущие диалоги, документы, факты. Для поиска используется векторный поиск.  
**Зачем это нужно:** Даёт Jarvis контекст и знания. Он сможет ссылаться на прошлые обсуждения и использовать информацию из локальных файлов пользователя для более точных и релевантных ответов (Retrieval-Augmented Generation).  
**Приоритет:** P1, **Сложность:** 6  

[ ] Выбрать и интегрировать локальную векторную базу данных (например, ChromaDB или FAISS).  
[ ] Реализовать процесс "индексации": превращение текста в векторы и сохранение в базе.  
[ ] Создать инструмент retriever, который агенты смогут использовать для поиска релевантной информации в этой базе.  
[ ] Написать тесты для проверки корректности вставки, поиска и удаления данных.  
[ ] Настроить логирование всех операций с долговременной памятью.

---

### 4.2. Эпизодическая / рабочая память  
**Что это:** "Блокнот" для текущей задачи. Это временное хранилище, где содержится весь контекст текущего диалога или проекта.  
**Зачем это нужно:** Позволяет Jarvis "держать в уме" всё, что относится к текущей задаче, не смешивая это с долговременными знаниями. Автоматическая очистка предотвращает бесконтрольный рост потребления памяти.  
**Приоритет:** P1, **Сложность:** 5  

[ ] Реализовать класс WorkingMemory для хранения контекста одной задачи.  
[ ] Внедрить механизм ограничения размера рабочей памяти (например, по количеству токенов или сообщений).  
[ ] Реализовать политику автоматической очистки устаревших данных (TTL - Time-To-Live).  
[ ] Написать тесты, проверяющие, что память не растёт бесконтрольно и корректно очищается.

## 5. Наблюдаемость и Качество  
Инструменты для мониторинга состояния системы и оценки её эффективности.

### 5.1. Трассировка и метрики (OpenTelemetry)  
**Что это:** "Приборная панель" Jarvis. Система, которая собирает все ключевые показатели производительности: время ответа, количество использованных токенов, ошибки, загрузку GPU.  
**Зачем это нужно:** Позволяет понимать, что происходит внутри системы, быстро находить узкие места и проблемы, а также отслеживать производительность в динамике.  
**Приоритет:** P1, **Сложность:** 7  

[ ] Интегрировать OpenTelemetry SDK в приложение.  
[ ] Настроить сбор ключевых метрик: латентность запросов, количество токенов (prompt/completion), количество ошибок.  
[ ] Реализовать экспорт метрик в Prometheus.  
[ ] Создать базовый дашборд в Grafana для визуализации собранных метрик.  
[ ] Настроить базовые алерты (например, если процент ошибок превышает 5%).

---

### 5.2. Эвалюации (Golden Set)  
**Что это:** Автоматизированная система тестирования качества ответов. У вас есть "золотой набор" (golden set) вопросов и эталонных ответов, и вы регулярно прогоняете тесты, чтобы убедиться, что после изменений Jarvis не стал отвечать хуже.  
**Зачем это нужно:** Обеспечивает стабильность качества. Это защита от регрессий, когда исправление в одном месте ломает что-то в другом.  
**Приоритет:** P1, **Сложность:** 6  

[ ] Создать "golden set" из как минимум 20 примеров (вопрос-ответ).  
[ ] Написать скрипт, который автоматически запускает Jarvis на вопросах из golden set и сохраняет его ответы.  
[ ] Реализовать механизм сравнения ответов Jarvis с эталонными (например, с помощью LLM-as-a-judge).  
[ ] Интегрировать запуск эвалюации в CI/CD пайплайн.

## 7. Горизонт Автономии: От Ассистента к Агенту  
Функции, превращающие Jarvis из инструмента в проактивного партнёра, способного работать самостоятельно.

### 7.1. Движок автономных целей (Autonomous Goals Engine)  
**Что это:** "Внутренний голос" Jarvis. Система, которая на основе общей директивы (например, "поддерживай порядок в моих проектах" или "оптимизируй мою работу") способна самостоятельно ставить себе высокоуровневые цели.  
**Зачем это нужно:** Это главный шаг к полной автономии. Jarvis перестаёт ждать конкретных команд и начинает сам искать, что можно улучшить или сделать, превращаясь в полноценного цифрового сотрудника.  
**Приоритет:** R, **Сложность:** 10  

[ ] Создать "агента-стратега", который периодически анализирует общее состояние системы и окружения.  
[ ] Реализовать механизм постановки долгосрочных целей (например, "повысить качество тестов в проекте X на 10%").  
[ ] Научить систему декомпозировать эти цели в конкретные, выполнимые задачи для основного движка.  
[ ] Создать UI для просмотра и утверждения (или отклонения) целей, предложенных Jarvis.

---

### 7.2. Проактивный мониторинг и триггеры  
**Что это:** "Глаза и уши" Jarvis. Способность системы следить за изменениями в указанных местах (папки с файлами, почтовый ящик, репозитории) и автоматически запускать задачи при наступлении событий.  
**Зачем это нужно:** Позволяет Jarvis реагировать на события в реальном мире без участия человека. Например, получив новый отчёт на почту, он может автоматически его проанализировать и подготовить саммари.  
**Приоритет:** P2, **Сложность:** 8  

[ ] Реализовать модуль мониторинга файловой системы для отслеживания создания/изменения файлов.  
[ ] Интегрировать модуль для чтения почты по IMAP/POP3.  
[ ] Создать систему "триггер-действие", где пользователь может настроить правила (например, "ЕСЛИ в папке 'inbox' появился .pdf, ТО запустить задачу 'анализ документа'").  
[ ] Настроить логирование всех проактивных действий, чтобы пользователь всегда знал, почему Jarvis начал ту или иную задачу.

---

### 7.3. Цикл самосовершенствования (Self-Improvement Loop)  
**Что это:** Способность Jarvis учиться на своих ошибках. После выполнения задачи специальный агент-критик анализирует результат и процесс, и если находит недостатки, автоматически создаёт новую задачу для их исправления.  
**Зачем это нужно:** Система становится "умнее" с каждой выполненной задачей. Если Jarvis плохо написал код, он сам это поймёт, проанализирует и в следующий раз постарается не повторять ошибку, улучшая свои внутренние промпты или алгоритмы.  
**Приоритет:** R, **Сложность:** 9  

[ ] Реализовать "агента-рефлексии", который анализирует логи завершённой задачи.  
[ ] Создать промпт для этого агента, чтобы он искал неэффективные шаги, неудачные промпты или ошибки.  
[ ] Если найден недостаток, система должна уметь автоматически создавать задачу в бэклоге (например, "улучшить промпт для генерации тестов").  
[ ] Внедрить A/B-тестирование для проверки, действительно ли новое решение лучше старого.
